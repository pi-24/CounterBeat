# CounterBeat

A first-person counter-strafe rhythm game. Bots appear in lanes on the beat;
you strafe into the lane, counter-strafe to a dead stop, and shoot on the
beat. Score comes from timing, how planted you were when you fired, and aim
(headshots). Built for CS and Valorant players, in the browser.

Six original tracks (90–170 BPM) at four difficulties each, a daily
challenge with its own leaderboard, your own songs charted automatically,
replays of any ranked run, and a timing profile on your page.

- Engine: [Babylon.js](https://www.babylonjs.com/) (tree-shaken `@babylonjs/core`), own Web Audio engine
- Build: [Vite](https://vite.dev/) multi-page site
- Accounts, leaderboard, settings sync: [Supabase](https://supabase.com/) (optional — the game runs fully offline without it)
- Anti-cheat: every run is recorded as an input log and replayed on the server; only the server-computed score is ranked

## Run it locally

```bash
npm install
npm run dev          # http://localhost:5173
```

With no `.env.local` the site uses the **local backend**: accounts, runs and
settings live in the browser's local storage, and runs are verified by the
same replay code running in the page. That is all you need for development
and for playing solo.

Other scripts:

```bash
npm run build        # production build to dist/
npm run preview      # serve dist/ on http://localhost:4173
npm run simulate     # play every chart with scripted bots and print scores
npm test             # replay-validator + beat-detector suites (must say "all good")
npm run sync-rules   # copy src/game/rules into the edge function (run before deploying it)
```

The beat-detector test needs the raw WAVs: `cd tools/asset-tools && python3
gen_audio.py` renders every track and effect into `audio_raw/` (numpy, and
scipy if present). Encode with ffmpeg into `public/audio/` as `.ogg` and
`.mp3`.

## Charts

A chart is a track at a difficulty, named by an id the server can resolve
too: `t:neon:hard`, `daily:2026-10-11`, `tutorial`, or
`custom:<hash>:<difficulty>`. `src/game/rules/charts.js` is the whole
catalogue. Each difficulty sets the lane count, how tight the stopping zone
is, the timing windows, the movement model and a target note density; the
density picks a bar pattern per track so Normal feels like Normal at 90 BPM
and at 170. Notes are generated from a seed, and a lane is only chosen when
the movement model says the dash is possible in the time available (with a
reaction allowance), so every chart is clearable by construction — the test
suite proves it with a scripted pilot.

Hard on a track unlocks when Normal on it is cleared, Expert when Hard is.

**Daily challenge:** `daily:<UTC date>` hashes the date to a track, a
difficulty (mostly Hard) and a seed, so everyone plays the same notes and the
server rebuilds the chart from the id. The edge function accepts a daily run
on its day plus a one-hour grace period. Rankings → "Daily challenge" shows
today's board.

**Your songs:** the menu's *Your songs* tab takes an audio file, decodes it
in the page, finds the tempo and first beat (`library/analyse.js`: spectral
flux onsets, a comb-filter tempogram with a prior around 128 BPM, geometric
mean to reject 3/2 and 4/3 tempo errors) and charts it at every difficulty
on that grid. The file stays in IndexedDB in that browser. Runs on custom
songs are stored as personal bests only — the server never hears the audio,
so it cannot verify the chart, and the database constraint
`runs_custom_unverified` keeps them off the rankings. ½× / 2× and ±20 ms
buttons fix the detector when it is wrong.

**Replays:** every stored run keeps its input log, and anyone can watch a
run from the rankings or a profile (`game.html?replay=<run id>`). The
replay drives the same simulation the validator uses, so it reproduces the
score exactly; the camera auto-aims at the next bot.

**Timing profile:** each run records a histogram of hit errors; the profile
page sums them and reports early/late bias, perfect, counter-strafe and
headshot rates.

## Movement

`rules/CounterStrafeBody.js` is the Source-engine ground model in one axis,
the one CS and Valorant hands already know: friction every tick,
proportional to speed with a floor (`stopSpeed`) so the last stretch brakes
at a fixed rate; holding a key adds `accel × maxSpeed` per second towards
full speed (a 16 ms tap is a 2–3 px nudge that friction eats in ~80 ms, a
hold reaches full speed in ~0.15 s); the opposite key is the same
acceleration pointed backwards on top of friction, which is the
counter-strafe — about 0.08 s to a dead stop from full speed against ~0.4 s
for a release. One `MOVEMENT` serves every official difficulty, as in the
games this is for - difficulty comes from the chart (lane count and spacing,
stop-zone width, timing windows, note density), not from faster feet.
Settings → Movement lets the player scale speed and acceleration by ±25% for
feel; the scale is written into the run log, so the server replays the run
with the same feet, and anything outside the range is refused as tampered.
Lane spacing is derived per chart from the tempo and the movement
(`trackScaleFor`), so a lane change always fits in the pattern's longest gap
and faster tracks pull the windows closer together; dense patterns thin out
on fast tracks for the same reason.

Changing anything in this file changes what every chart demands and how
every stored replay plays back, so bump `LOG_VERSION` in `rules/config.js`
when you do (the validator refuses older logs rather than misjudging them;
the replay viewer still plays version 3 logs with the rules they were
recorded under).

## How the anti-cheat works

The client never decides a ranked score. While you play, `RunRecorder`
logs the length of every simulation tick, every strafe-input change, and
every shot (song time, which bot the hit-scan found, body/head, blocked).
The movement model is deterministic given those ticks, so the server feeds
the log through the very same `rules/` code, lands on the same positions and
speeds, re-judges every shot and recomputes the score. The run is stored
with the **server's** score and marked `verified`. Logs that do not replay
(wrong lane for a claimed hit, too many shots per second, implausibly
perfect timing, a shot stamped off its tick's time) are refused and nothing
is stored.

Every tick is applied in one order on both sides (inputs, movement, spawn
notes, expire missed notes, shots) and a shot is judged at its tick's own
time, never at a time the client claims. A ranked run also needs a one-use
token that the server issues when the run starts and spends when it is
submitted, at least as long after as the run lasted, and each stored log is
fingerprinted, so a replay copied from the rankings cannot be resubmitted
under another name. None of this stops someone who writes a whole input
log with a bot: the rules are replayed exactly, but the player's hands are
only ever the client's word.

The simulation clock follows a smoothed audio clock and sub-steps through
frame stalls (never more than 50 ms per tick), and the body is caught up
to the instant of each shot, back-dated to when the click happened, so
honest runs on slow or hitching machines still replay exactly.

`tools/test-validate.mjs` covers the honest cases (levels 0–3, jittered
frame lengths) and the cheats it must catch. Run it whenever you touch
anything in `src/game/rules/`.

## Setting up Supabase (real accounts + shared leaderboard)

1. Create a project at <https://supabase.com/dashboard>. Note the **Project
   URL** and the **anon public key** (Project Settings → API).

2. Apply the schema. Either paste `supabase/migrations/0001_init.sql`,
   `0002_charts.sql` and `0003_hardening.sql` into the SQL editor and run
   them in order, or with the CLI:

   ```bash
   npm i -g supabase
   supabase login
   supabase link --project-ref <your-project-ref>
   supabase db push
   ```

   This creates `profiles` (auto-created from `auth.users`, with a unique
   display name and a `settings` JSON column), `runs` (with chart ids, the
   replay log and timing stats), the row-level security policies (anyone can
   read; nobody can insert runs directly — only the edge function with the
   service role can), and the `leaderboard(chart_filter)` and
   `run_replay(id)` functions. `0003_hardening.sql` adds the `run_tokens`
   table, the unique log fingerprint on `runs`, the `player_progress(player)`
   function (bests and clears over every run, not just recent ones) and a
   sign-up trigger that cleans display names instead of failing.

3. Deploy the run-verification function:

   ```bash
   npm run sync-rules
   supabase functions deploy submit-run
   ```

   The hosted environment provides `SUPABASE_URL`, `SUPABASE_ANON_KEY` and
   `SUPABASE_SERVICE_ROLE_KEY` automatically; no secrets to set. Re-run both
   commands whenever `src/game/rules/` changes, or the server will reject
   runs played with newer rules.

4. Auth settings (Authentication → URL Configuration): set **Site URL** to
   your deployed origin (e.g. `https://counterbeat.vercel.app`) and add
   `https://counterbeat.vercel.app/**` and `http://localhost:5173/**` to
   **Redirect URLs** (Discord login returns to `/game.html`, email
   confirmation to `/login.html`).

   Email/password works out of the box. If you want *no* confirmation
   email during development, turn off "Confirm email" under Authentication →
   Providers → Email; the register page handles both modes.

5. Optional — Discord login. Create an application at
   <https://discord.com/developers/applications>, add the redirect
   `https://<project-ref>.supabase.co/auth/v1/callback` under OAuth2, then
   enable the Discord provider in Supabase with the client ID and secret.
   The "Continue with Discord" button appears automatically when the
   Supabase backend is active.

6. Point the site at the project. Locally, create `.env.local`:

   ```
   VITE_SUPABASE_URL=https://<project-ref>.supabase.co
   VITE_SUPABASE_ANON_KEY=<anon key>
   ```

   On Vercel add the same two variables under Project → Settings →
   Environment Variables, then redeploy. If either is missing the site
   silently falls back to the local backend.

## Deploying on Vercel

The repo root is the project (there is no `website/` sub-folder any more).
`vercel.json` already sets the framework to Vite, build command `vite build`
and output `dist`, so in the Vercel project settings:

- **Root Directory**: leave empty (repo root). If it is still set to
  `website` from the old layout, clear it.
- **Framework Preset**: Vite (auto-detected).
- **Environment Variables**: `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`,
  optionally `VITE_SENTRY_DSN` and `VITE_APP_VERSION=$VERCEL_GIT_COMMIT_SHA`.

Every push to `main` then builds and deploys.

## Error reporting (optional)

Set `VITE_SENTRY_DSN` to a [Sentry](https://sentry.io) browser DSN. The SDK
is only bundled when the variable is present at build time and loads as a
separate chunk, so builds without it ship nothing extra. Errors are tagged
with the page and backend kind; no personal data is sent.

## Audio-offset calibration

Settings also has toggles for the beat ring around the crosshair and the
upcoming-beats strip, for players who want a cleaner screen.

Settings → Timing → **Calibrate**. A 120 BPM click plays; tap SPACE or click
on each click for sixteen beats. The median tap offset is stored as
`audioOffset` (clamped to ±250 ms), applied to the song position when judging,
and synced to the account when logged in. Bluetooth headphones typically
measure +100–200 ms.

## Playing

| Key | Action |
| --- | --- |
| A / D | strafe |
| Left click | fire |
| Mouse | aim (pointer lock) |
| Esc | pause |
| T | start the tutorial from the menu |
| Q | leave a replay |

Counter-strafe (tap the opposite key for an instant) to stop dead: a shot
while planted is worth far more than one while sliding, and the spread cone
grows with speed.
